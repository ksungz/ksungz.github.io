2년쯤 전, 개인 개발 환경의 뼈대를 잡았다. 지금처럼 여러 AI 에이전트가 같은 자료를 읽고 일을 이어가는 구조를 처음부터 만든 건 아니었다. Obsidian에 프로젝트 문서를 쌓고 에이전트를 바꿔 쓰면서 규칙과 작업 기록을 조금씩 붙였다.

이제는 문서를 어디에 적을지보다 **새 세션이 무엇부터 읽어야 하는지**가 더 신경 쓰인다. 작업 기록을 제대로 남겨도 다음 에이전트가 예전 결정을 최신 결정으로 읽으면 다시 설명해야 한다. 실제 인계 기록을 돌아보며 지금 방식에서 무엇을 남기고 어디를 손볼지 정리했다.

## 오래 쓰는 규칙과 지금 할 일

- 저장소의 `AGENTS.md`에는 작업 전에 읽을 문서와 수정·검증·배포 규칙을 둔다.
- Obsidian의 프로젝트 노트에는 배경과 오래 참고할 결정을 남긴다.
- 작업 문서에는 이번 목표, 담당자와 수정 범위, 확인 결과, 남은 일을 적는다. 일을 이어받을 때는 이 문서와 실제 코드 변경분을 먼저 본다.

같은 파일을 두 에이전트가 동시에 고치면 어느 변경이 테스트를 통과했는지부터 다시 맞춰야 한다. 그래서 수정 담당을 정해 두고, 검토하는 쪽은 문제를 발견하면 재현 조건과 기대 결과를 남긴다.

## Claude Code가 고치고 Codex가 다시 확인했다

한 업무 시뮬레이션을 검토할 때 Codex가 실패 응답이 나왔는데도 내부 상태가 바뀌는 경우를 찾았다. 화면만 보면 다시 눌러도 될 것 같지만, 시스템은 요청을 이미 한 번 처리한 상태였다.

인계 문서에는 **실패할 때는 상태가 그대로여야 하고, 정상 요청과 재시도는 기존대로 동작해야 한다**고 적었다. Claude Code가 보완한 뒤 Codex가 변경분을 검토하고 문제가 나왔던 흐름을 다시 실행했다. 재검토에서 통과한 범위는 그때 확인한 코드와 입력으로 한정했다. 별도 환경 확인과 배포는 남은 일로 구분했다.

당시 인계 기록을 간추리면 이렇다.

- **인계 시점:** 수정 완료, 재검토 대기
- **확인할 것:** 실패 응답 뒤 상태가 바뀌지 않는지, 정상 요청과 재시도는 유지되는지
- **판단 근거:** 변경 파일, 재현 조건, 실행한 테스트와 결과
- **남은 일:** 별도 환경 확인과 배포

## 이제 손볼 세 가지

실제로 최신 지시가 어느 문단에 있는지 안내가 엇갈려 바로잡은 적이 있다. 문서를 더 많이 쓰기보다, 새 세션이 읽을 순서와 최신 기준을 먼저 정리할 때가 됐다.

1. **시작점을 하나로 좁힌다.** 프로젝트 시작 문서에서 현재 진행 중인 작업 문서로 바로 연결한다. [Obsidian 검색](/tech/obsidian-rag)은 과거에 왜 그런 결정을 했는지 찾아볼 때 쓰고, 최신 상태는 작업 문서와 현재 코드를 맞춰 본다.
2. **검증 결과는 확인한 변경에 붙인다.** 테스트가 통과했다고만 쓰지 않고 어떤 변경을 대상으로 무엇을 실행했는지 기록한다. 다른 환경에서의 확인이나 배포가 남아 있으면 같은 줄에 묶지 않는다.
3. **대화 내역 없이 재개해 본다.** 다음 작업에서 새 세션에 프로젝트 시작 문서만 건네고, 코드를 고치기 전에 현재 상태와 수정해도 되는 범위, 다음 확인 항목을 짚게 한다. 이전 기록과 비교해서 놓친 내용이 있으면 문서부터 고친다.

아직 이 개선안을 모두 적용한 건 아니다. 다음 작업에서 먼저 확인할 건 에이전트가 바뀌어도 내가 앞선 결정을 다시 설명하지 않고 재개할 수 있는지다.
