한 에이전트에게 구현을 맡기고 다른 에이전트에게 검토를 부탁하면, 새 에이전트는 무엇을 고치기로 했고 어디까지 확인했는지부터 알아야 합니다. 대화를 통째로 넘기면 처음에 논의한 안과 최종 결정이 섞입니다. 그래서 작업을 다시 시작하는 데 필요한 정보는 채팅 밖에 남기기로 했습니다.

## 오래 쓰는 규칙과 지금 할 일을 나눴습니다

- **저장소 규칙:** `AGENTS.md`에서 작업 전에 확인할 것과 수정·검증·배포의 기준을 정합니다.
- **프로젝트 노트:** Obsidian에 프로젝트의 배경과 오래 참고할 결정을 남깁니다.
- **작업 문서:** 이번 목표와 담당자, 수정 범위, 검증 결과, 미확인 항목을 적습니다. 작업을 이어받을 때는 이 문서와 실제 코드 변경분을 먼저 봅니다.

같은 작업의 수정 담당은 한 번에 한 쪽으로 정했습니다. 검토하는 쪽에서 문제를 발견하면 같은 파일을 바로 고치기보다 재현 조건과 기대 결과를 남깁니다. 그래야 다음 검토에서 어떤 변경을 확인하는지 알 수 있습니다.

## Claude Code가 보완하고 Codex가 다시 확인한 사례

한 업무 시뮬레이션을 검토하다가 화면에 실패 응답이 표시됐는데 내부 상태는 이미 바뀐 경우를 발견했습니다. 사용자 입장에서는 다시 눌러도 될 것 같지만, 시스템은 요청을 한 번 처리한 상태였습니다.

Codex의 검토 결과를 바탕으로 **실패를 반환하면 상태는 그대로여야 하고, 정상 요청과 재시도는 기존대로 동작해야 한다**는 기준을 작업 문서에 남겼습니다. Claude Code가 코드를 수정한 뒤에는 Codex가 변경분을 검토하고 문제가 나왔던 흐름을 다시 실행했습니다. 이때 확인한 테스트 결과와 나중에 해야 할 별도 환경 확인·배포를 나눠 기록했습니다.

당시 인계 기록을 공개용으로 간추리면 다음과 같습니다.

- **현재 상태:** 수정 완료, 독립 재검토 대기
- **다음에 볼 것:** 실패 응답을 받은 뒤 상태가 그대로인지 확인
- **함께 볼 것:** 정상 요청과 재시도, 변경 파일과 테스트 결과
- **남은 일:** 별도 환경 확인과 배포

## 인계 문서가 대신할 수 없는 일

문서가 있다고 해서 새 에이전트가 알아서 규칙을 지키는 건 아닙니다. 새 세션에는 먼저 읽을 문서를 알려주고, 적혀 있는 상태가 현재 코드와 맞는지 확인합니다. 예전 테스트 결과는 참고하되 지금 검토하는 변경까지 통과했다고 보지는 않습니다.

[Obsidian 검색 환경](/tech/obsidian-rag)은 예전에 어떤 결정을 했는지 찾는 데 씁니다. 작업 문서는 그중 지금 적용할 기준과 다음에 할 일을 좁혀 줍니다. 둘을 구분해 두면 도구를 바꿔도 결정부터 다시 설명하거나, 아직 확인하지 않은 일을 완료로 넘기지 않고 작업을 이어갈 수 있습니다.
