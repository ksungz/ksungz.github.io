2년쯤 전 개인 개발 환경의 뼈대를 잡았다. 처음부터 여러 에이전트가 일을 이어받는 환경을 목표로 한 건 아니었다. Obsidian에 프로젝트를 정리해두고 Codex와 Claude Code를 번갈아 쓰다 보니 대화 밖에 남겨야 할 기록이 하나씩 늘었다. 이전 결정을 다시 설명하거나 테스트 결과가 어느 변경에 해당하는지 찾아보는 일이 생겼기 때문이다.

하네스 엔지니어링 관점에서 보면 이 문제는 프롬프트를 고치는 것만으로 해결하기 어렵다. **새 세션이 어떤 상태에서 시작하고, 어디까지 바꿀 수 있으며, 무엇을 확인해야 작업이 끝났다고 볼지**가 환경에 드러나야 한다. [OpenAI의 하네스 엔지니어링 사례](https://openai.com/index/harness-engineering/)는 저장소 지식의 탐색 경로와 기계적으로 검사할 수 있는 규칙을 다룬다. [Anthropic의 장기 작업 하네스 실험](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)은 세션 사이에 진행 기록과 Git 상태를 남겨 다음 작업자가 이어받게 했다. 내 환경에서 비슷한 역할을 한 것은 문서 한 장이 아니라 그 기록을 읽고, 수정하고, 다시 검증하는 흐름이었다.

## 시작할 때 읽는 기록과 실행 중 지킬 범위

**시작 문맥.** `AGENTS.md`에는 작업 전 읽을 문서와 저장소 규칙을 둔다. Obsidian의 프로젝트 노트에는 배경과 오래 참고할 결정을 남기고, 진행 중인 작업의 담당자와 상태는 작업 문서에서 확인한다. [Obsidian 검색](/tech/obsidian-rag)은 과거 결정을 찾는 데 쓴다. 검색 결과가 비슷하다고 해서 지금 적용할 기준이라는 뜻은 아니다. 현재 상태는 진행 중인 기록을 Git의 브랜치와 실제 변경분에 대조해 판단한다.

**소유권과 검증.** 작업 문서에는 `owner`, `scope`, `depends_on`, `handoff_to`를 둔다. 누가 어느 범위를 맡는지, 어떤 작업을 먼저 마쳐야 하는지, 다음에 누가 받을지 적는다. 수정 담당과 검토 담당이 같은 파일을 동시에 바꾸지 않도록 했고, 작업을 넘길 때는 변경 파일과 실행한 검사, 확인하지 못한 항목을 남긴다.

여기서 문서 규칙과 도구가 강제하는 제약은 구분한다. 로컬 검사 스크립트는 작업 문서의 필수 항목과 선행 작업 참조, 완료 기록이 있는지 확인한다. 하지만 `scope`에 적힌 범위 밖 파일을 수정하지 못하게 막거나, 테스트 결과가 실제 코드와 일치한다고 보증하지는 않는다. 그 부분은 변경분을 검토하고 검사를 다시 실행해 확인한다.

## 인계 문서에 검토 기준을 남겼다

한 업무 시뮬레이션에서 Codex가 실패 응답이 나왔는데도 내부 상태는 바뀌는 경우를 발견했다. 화면만 보면 다시 시도해도 될 것 같지만, 시스템은 이미 요청을 처리한 상태였다. 인계 문서에는 **실패하면 상태가 그대로여야 하고, 정상 요청과 재시도는 기존처럼 동작해야 한다**고 적었다. 수정 방법을 지시하는 것보다 어떤 동작이 유지돼야 하는지 남기는 편이 검토에 도움이 됐다.

Claude Code가 보완한 뒤 Codex가 검토 대상 파일의 해시를 대조하고 같은 요청을 다시 실행했다. 응답만 바뀐 것이 아니라 실패 뒤 상태도 그대로인지 확인했다. 검토 통과는 그때 확인한 코드와 테스트 범위에만 적용했고, 별도 환경 확인과 배포는 남은 일로 뒀다.

다음 에이전트에 넘긴 것은 ‘수정 완료’라는 결론만이 아니었다. **무엇을 검토했고, 어느 변경에서 확인했으며, 그 결과를 어디까지 믿을 수 있는지**를 남겼다. 그래야 새 세션도 변경이 더 들어왔을 때 이전 통과 판정을 그대로 가져다 쓰지 않는다.

## 다음 개선은 새 세션으로 시험한다

최신 지시를 어느 문단에서 읽어야 하는지 안내가 엇갈려 고친 적도 있다. 지금 환경을 손본다면 도구를 더 연결하기보다, **방금 시작한 세션이 올바른 상태에서 출발하는지**부터 확인하고 싶다.

1. **현재 작업을 찾는 경로를 하나로 좁힌다.** 프로젝트 시작 문서에서 진행 중인 작업으로 연결하고 완료 기록은 이력으로 구분한다.
2. **검증 결과에 대상 변경을 같이 남긴다.** 커밋한 코드는 커밋 ID로, 아직 커밋 전이면 변경 파일의 해시로 대조한다. 대상이 달라졌을 때는 이전 결과를 근거로 완료 처리하지 않는다.
3. **대화 없이 시작하는 읽기 전용 테스트를 해본다.** 새 세션에 시작 문서만 건넨 뒤 현재 작업, 수정 범위, 완료·미확인 항목, 다음 행동을 답하게 한다. 기존 기록과 비교해 하나라도 빠지면 그 이유부터 찾는다.

세 가지는 앞으로 적용하고 시험할 계획이다. 모델을 바꿔도 앞서 내린 결정과 검증 범위가 그대로 전달되는지, 그때 내가 다시 설명해야 하는 일이 줄어드는지부터 확인하려 한다.
