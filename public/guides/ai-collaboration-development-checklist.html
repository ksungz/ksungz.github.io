가장 중요한 한 문장

작게 요청하고, 직접 검증하고, 결정과 근거를 설명한다.

업무를 AI가 다룰 수 있는 단위로 나누고, 필요한 맥락과 완료 조건을 전달한다. 결과는 사람이 실행해 검증하고 중요한 선택과 남은 한계를 자기 말로 설명한다.

01 · 지시 완료 조건까지 작게 나누기
02 · 검증 테스트와 화면으로 직접 확인
03 · 설명 선택 이유와 한계를 설명하기

작업 전 정렬

코드를 수정하기 전에 목적, 범위, 확인 기준을 팀과 맞춘다.

첫 10분
하나의 주 에이전트로 시작한다. 여러 AI를 동시에 열기보다 작업 맥락을 한곳에 유지한다. 다른 도구는 교차 검토나 명확한 역할이 있을 때만 추가한다.
  • 이슈·기획 문서·운영 요청 중 무엇이 기준 문서인지 확인
  • 목표, 비목표, 완료 조건과 담당 범위를 구분
  • 사내 정보·개인정보·인증 정보가 입력에 포함되는지 확인
  • 실행·테스트·빌드 명령과 배포 영향 범위 확인
  • 불명확한 정책은 추측하지 말고 담당자에게 질문
  • 시간 제한이 있다면 화면 타이머를 기준으로 구현·검증·마감 구간을 먼저 배분

도구와 설정 선택

설정 자체보다 문제를 풀고 검증하는 데 필요한 최소한만 선택한다.

필요할 때만
기본 제공 도구만으로 시작해도 충분하다. 익숙하지 않은 도구를 추가하면 맥락이 흩어지고, 설정과 결과를 직접 설명하기 어려워질 수 있다. 하나의 주 도구로 시작하고 실제 필요가 확인될 때만 확장한다.

주 에이전트

가장 익숙한 도구 하나에 요구사항, 변경 과정과 오류 맥락을 유지한다.

과제 도우미·시나리오 에이전트

요구사항, 화면 사용법, 제출 흐름과 과제 맥락을 확인하되 답을 대신 만들게 하지는 않는다.

Skills·MCP

반복 규칙이나 외부 연결이 실제로 필요하고 보안·권한 기준이 확인됐을 때만 사용한다.

추가 도구

교차 검토처럼 역할이 분명할 때만 추가하고, 같은 작업을 여러 도구에 중복 요청하지 않는다.

제공 환경

준비된 실행 환경과 우선 정책을 먼저 확인하고 관리 영역·필수 프로세스·예약 포트를 바꾸지 않는다.

선택 기준

왜 이 도구가 필요한지 한 문장으로 설명할 수 없다면 기본 도구를 유지한다.

실전 진행 순서

AI가 완료했다고 말해도 다음 단계로 자동 이동하지 않는다.

순서대로 진행
01

업무 요청부터 나눈다

바로 코드를 만들지 말고 기능, 제약, 완료 조건, 불명확한 점을 먼저 구분한다.

  • 이슈·기획 문서·과제 안내와 관련 링크를 에이전트에 전달한다.
  • 추측이 필요한 부분은 요청자, 담당자 또는 제공된 과제 도우미에게 확인한다.
  • 요구하지 않은 기능은 만들지 않는다.
02

수정 전 상태를 실행한다

프로젝트 구조와 명령어를 확인하고 기존 테스트·빌드·화면 상태를 기록한다.

  • package.json 또는 프로젝트 실행 문서를 확인한다.
  • 처음부터 실패하던 항목과 수정 후 실패한 항목을 구분한다.
  • 보이는 오류 메시지를 숨기지 않는다.
03

최소 변경 계획을 확인한다

수정 파일, 구현 순서, 검증 방법을 확인한 뒤 첫 단계만 시작한다.

  • 기존 구조를 유지하는 방식을 우선한다.
  • 새 라이브러리와 대규모 리팩터링은 명확한 이유가 있을 때만 허용한다.
  • 이해하지 못한 설계가 나오면 쉬운 말로 다시 설명하게 한다.
  • 시간 제한이 있다면 핵심 완료 조건을 먼저 만족시키고 선택 기능은 뒤로 미룬다.
04

한 단계씩 구현한다

한 번에 전체를 맡기지 않고 핵심 기능부터 작은 단위로 구현한다.

  • 변경 파일과 이유를 매번 확인한다.
  • 단계가 끝날 때마다 관련 테스트를 실행한다.
  • 오류가 발생하면 정확한 오류 메시지를 기준으로 수정한다.
05

화면과 예외 상황을 직접 본다

테스트 통과만으로 끝내지 않고 실제 브라우저에서 사용자 흐름을 확인한다.

  • 정상 입력, 빈 입력, 잘못된 입력, 결과 없음
  • 로딩, 오류, 반복 실행, 긴 텍스트
  • 콘솔 오류와 화면 깨짐 여부
06

최종 diff와 전체 검증을 한다

요구사항 누락, 과도한 구현, 불필요한 파일, 비밀값 노출과 인계 내용을 확인한다.

  • 전체 테스트와 빌드를 다시 실행한다.
  • AI가 추측해서 만든 API나 기능이 없는지 확인한다.
  • 중요한 결정, 남은 한계, 롤백 방법을 설명할 수 있게 정리한다.
  • 제출 전에는 새 기능보다 동작하는 상태와 검증 기록을 우선한다.
07

제출 자료를 확인하고 끝까지 완료한다

결과물뿐 아니라 작업 기록과 테스트 결과가 함께 제출된다는 전제로 마지막 상태를 확인한다.

  • 제출 미리보기에서 결과물과 자동 수집된 작업 기록의 범위를 확인한다.
  • 제출 후 확인 질문까지 답해야 최종 제출이라는 점을 기억한다.
  • 코드를 보지 않고도 핵심 파일, 설계 이유, 예외 처리와 검증 결과를 자기 말로 설명한다.

작업 주기 배분

작업 크기와 관계없이 구현에만 몰리지 않도록 전체 주기를 비율로 나눈다.

권장 비율
10% 업무 정렬

목표·비목표·완료 조건·질문 정리

15% 기준 상태

구조 확인, 테스트, 빌드, 화면 실행

45% 단계별 구현

핵심부터 작게 구현하고 매번 검증

25% 검증·리뷰

예외 상태, 전체 테스트, 보안과 diff 검토

5% 공유·인계

선택 이유, 검증 결과, 한계와 롤백 정리

화면 타이머가 기준이다. 종료 시점에는 편집과 추가 작업이 멈출 수 있으므로 마지막 검증을 작업 시간 안에 마친다. 제출 후 확인 질문에는 별도 시간이 주어지는 환경이라면, 질문 시간을 확보하려고 구현 시간을 미리 줄일 필요는 없다.

시간 제한 AI 평가에 적용

평가에서는 결과물과 함께 문제를 나누고 지시하고 검증한 과정, 결과에 대한 이해를 본다.

응시 흐름
시작 전

환경과 운영 경계를 먼저 확인

  • 카메라·브라우저·인터넷과 연습 세션 확인
  • 저장, 터미널, 미리보기, AI 채팅과 제출 흐름 체험
  • 플랫폼 관리 영역과 금지 명령 확인
진행 중

타이머와 근거를 함께 관리

  • 핵심 완료 조건부터 작은 단위로 구현
  • 채팅·터미널·설정·변경·테스트 기록이 남는다고 가정
  • 막히면 도우미로 요구사항과 화면 흐름 확인
제출 후

본인의 말로 구현을 설명

  • 제출 미리보기와 업로드 완료 상태 확인
  • 질문 생성 중에는 화면을 유지하고 대기
  • 모듈 역할, 설계 이유, 예외 처리와 검증 방법 답변
작업 기록은 따로 꾸미지 않는다. 무엇을 시도했고 어떤 결과를 버렸는지, 실패를 어떻게 좁혔는지가 자연스럽게 남도록 실제 명령과 검증 결과를 기준으로 진행한다. 안내문과 플랫폼 정책이 이 페이지보다 항상 우선한다.

복사해서 사용할 프롬프트

업무 요청, 과제 안내, 도우미 답변, 남은 시간과 현재 오류를 추가해서 사용한다.

Codex CLI
1. 요구사항 분석 
아직 코드는 수정하지 마.

아래 업무 요청을 기준으로 다음을 정리해줘.

1. 반드시 구현해야 하는 기능
2. 지켜야 하는 제약
3. 완료 여부를 확인할 기준
4. 불명확해서 확인이 필요한 내용
5. 예상 수정 파일
6. 구현 후 실행할 테스트
7. 남은 시간을 기준으로 한 구현·검증·마감 순서

각 판단은 과제 문구나 확인한 파일을 근거로 설명해줘.
불명확한 항목은 추측하지 말고 과제 도우미에게 물어볼 질문으로 정리해줘.
요구사항에 없는 기능은 추가하지 마.
2. 현재 상태 확인 
현재 프로젝트 구조와 실행 방법을 확인해줘.

아직 기능 코드는 수정하지 마.

1. 실행·테스트·빌드 명령 확인
2. 기존 테스트와 빌드 실행
3. 현재부터 실패하는 항목 정리
4. 업무와 직접 관련된 파일 확인
5. 기존 구조를 유지하는 최소 변경 계획 제시
6. 제공 환경의 정책과 건드리면 안 되는 관리 영역 확인

각 판단의 근거가 된 파일도 함께 알려줘.
3. 한 단계만 구현 
전체 계획 중 첫 번째 단계만 구현해줘.

기존 구조를 최대한 유지하고,
불필요한 라이브러리 추가나 대규모 리팩터링은 하지 마.
플랫폼 관리 영역, 필수 프로세스와 예약 포트는 변경하지 마.

완료 후 다음을 알려줘.

- 변경한 파일
- 변경한 이유
- 내가 직접 확인해야 할 코드
- 실행한 검증 명령과 결과
- 아직 구현하지 않은 다음 단계
4. 변경 검토 
현재 변경 내용을 업무 요구사항과 비교해 검토해줘.

다음을 구분해서 알려줘.

1. 충족한 요구사항
2. 아직 누락된 요구사항
3. 요구사항보다 과하게 구현한 부분
4. 추측해서 만든 기능이나 API
5. 오류·빈 상태·경계값 처리 누락
6. 추가로 실행해야 할 테스트

테스트 결과만 믿지 말고 실제 변경 코드도 검토해줘.
5. 제출 전 최종 점검 
제출 전 최종 점검을 진행해줘.

남은 시간: [여기에 입력]

1. 전체 요구사항 체크
2. 전체 테스트와 빌드 실행
3. 브라우저에서 확인할 사용자 흐름 정리
4. 불필요한 파일과 변경 확인
5. 비밀값이나 환경 정보 노출 확인
6. 현재 남은 한계 정리
7. 지금부터는 새 기능보다 동작 상태 보존을 우선해야 하는지 판단

실패한 항목이 있으면 완료라고 표현하지 말고
원인과 현재 상태를 그대로 알려줘.
6. 제출·확인 질문 준비 
제출 후 확인 질문에 대비할 수 있도록
이번 변경을 내가 직접 설명하기 위한 개요만 정리해줘.

1. 무엇을 구현했는가
2. 왜 이 방식으로 구현했는가
3. AI가 제안했지만 사용하지 않은 방법은 무엇인가
4. 예외 상황을 어떻게 처리했는가
5. 어떤 테스트를 직접 실행했는가
6. 아직 남아 있는 한계는 무엇인가

전문용어를 줄이고, 실제 변경 코드의 근거를 함께 표시해줘.
내가 확인하지 않은 내용은 새로 만들지 마.

추측한 답변이나 내가 실행하지 않은 검증은 만들지 마.
이 개요는 그대로 제출하지 않고 실제 코드를 다시 확인한 뒤
AI 창을 보지 않고 내 말로 설명할게.
7. 시간이 임박했을 때 마감 
남은 시간이 [N분]이야. 새 기능 구현은 시작하지 마.

현재 변경을 제출 가능한 상태로 마감해줘.

1. 핵심 완료 조건이 실제로 동작하는지 확인
2. 가장 빠르고 중요한 테스트만 실행
3. 실패한 테스트와 미완료 항목을 숨기지 않고 구분
4. 불필요한 파일, 비밀값, 디버그 코드 확인
5. 플랫폼 관리 영역과 필수 프로세스 변경 여부 확인
6. 제출 후 내가 설명해야 할 핵심 파일과 선택 이유 요약

파괴적 정리 명령, 대규모 리팩터링, 새 라이브러리 추가는 하지 마.
현재 동작하는 상태를 깨뜨릴 위험이 있는 변경은 먼저 경고해줘.

모두 구현하라는 뜻이 아니라, 확인 여부와 이유를 알고 있어야 한다.

직접 확인

기능

핵심 사용자 흐름이 처음부터 끝까지 동작하는가?

입력

빈 값, 잘못된 값, 긴 값, 중복 실행을 처리하는가?

상태

로딩, 결과 없음, 오류 상태가 사용자에게 보이는가?

기술

테스트·빌드가 통과하고 콘솔 오류가 없는가?

범위

요구하지 않은 기능과 불필요한 리팩터링이 없는가?

근거

중요한 선택을 왜 했는지 코드와 실행 결과로 설명할 수 있는가?

리뷰·제출 전 설명

코드만 넘기지 않고 판단과 검증 결과를 다른 사람에게 자기 말로 설명한다.

팀 공유

무엇을 바꿨나요?

변경한 기능, 파일, 사용자 흐름을 짧게 설명한다.

왜 이 방식인가요?

기존 구조 유지, 구현 범위, 다른 선택지를 쓰지 않은 이유를 말한다.

예외는 어떻게 처리했나요?

빈 입력, 실패, 로딩, 결과 없음 중 실제로 확인한 내용을 답한다.

어떻게 검증했나요?

실행한 테스트 명령과 브라우저에서 확인한 흐름을 구체적으로 말한다.

AI 제안을 그대로 썼나요?

검토 후 수정하거나 제외한 부분과 그 이유를 설명한다.

남은 한계는 무엇인가요?

못 한 부분을 숨기지 말고 시간과 범위를 기준으로 솔직하게 답한다.

마지막에는 AI 창을 보지 않고 60초 동안 설명한다. 핵심 파일의 역할, 선택한 방식, 예외 처리, 직접 실행한 검증과 남은 한계를 실제 코드와 실행 결과를 근거로 자기 말로 설명한다. 막히는 부분이 있으면 제출이나 인계 전에 코드를 다시 확인한다.

팀 사용 원칙

AI의 작업 범위와 사람이 승인해야 할 경계를 먼저 정한다.

운영 안전

파괴적 명령

git clean -fdx, 전체 삭제, 광범위한 프로세스 종료처럼 복구하기 어려운 명령은 승인 없이 실행하지 않는다.

평가 플랫폼 관리 영역

플랫폼이 관리하는 디렉터리, 런타임, 원격 연결 프로세스와 예약 포트는 수정하거나 종료하지 않는다.

운영 설정

배포, 인증, 권한, 데이터 삭제와 외부 전송처럼 영향이 큰 변경은 별도 검토와 담당자 승인을 거친다.

도구 사용

기록과 공유

결정 근거, 실행한 테스트, 남은 한계와 롤백 방법을 이슈·PR·작업 문서에 남긴다.
