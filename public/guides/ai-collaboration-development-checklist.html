업무를 AI가 다룰 수 있는 단위로 나누고, 필요한 맥락과 완료 조건을 전달한다. 결과는 사람이 실행해 검증하고 중요한 선택과 남은 한계를 팀에 공유한다.

작업 전 정렬

코드를 수정하기 전에 목적, 범위, 확인 기준을 팀과 맞춘다.

첫 10분
하나의 주 에이전트로 시작한다. 여러 AI를 동시에 열기보다 작업 맥락을 한곳에 유지한다. 다른 도구는 교차 검토나 명확한 역할이 있을 때만 추가한다.
  • 이슈·기획 문서·운영 요청 중 무엇이 기준 문서인지 확인
  • 목표, 비목표, 완료 조건과 담당 범위를 구분
  • 사내 정보·개인정보·인증 정보가 입력에 포함되는지 확인
  • 실행·테스트·빌드 명령과 배포 영향 범위 확인
  • 불명확한 정책은 추측하지 말고 담당자에게 질문

도구와 설정 선택

설정 자체보다 문제를 풀고 검증하는 데 필요한 최소한만 선택한다.

필요할 때만
기본 제공 도구만으로 시작해도 충분하다. 익숙하지 않은 도구를 추가하면 맥락이 흩어지고, 설정과 결과를 직접 설명하기 어려워질 수 있다. 하나의 주 도구로 시작하고 실제 필요가 확인될 때만 확장한다.

주 에이전트

가장 익숙한 도구 하나에 요구사항, 변경 과정과 오류 맥락을 유지한다.

Skills

반복되는 규칙과 작업 순서를 재사용할 때만 사용하고, 내용과 동작을 직접 이해한다.

MCP

외부 문서나 시스템 연결이 실제로 필요하고 보안·권한 기준이 확인됐을 때만 연결한다.

추가 도구

교차 검토처럼 역할이 분명할 때만 추가하고, 같은 작업을 여러 도구에 중복 요청하지 않는다.

제공 환경

준비된 실행 환경과 정책을 먼저 확인하고 관리 영역이나 기본 설정을 불필요하게 바꾸지 않는다.

선택 기준

왜 이 도구가 필요한지 한 문장으로 설명할 수 없다면 기본 도구를 유지한다.

실전 진행 순서

AI가 완료했다고 말해도 다음 단계로 자동 이동하지 않는다.

순서대로 진행
01

업무 요청부터 나눈다

바로 코드를 만들지 말고 기능, 제약, 완료 조건, 불명확한 점을 먼저 구분한다.

  • 이슈·기획 문서와 관련 링크를 에이전트에 전달한다.
  • 추측이 필요한 부분은 요청자 또는 담당자에게 확인한다.
  • 요구하지 않은 기능은 만들지 않는다.
02

수정 전 상태를 실행한다

프로젝트 구조와 명령어를 확인하고 기존 테스트·빌드·화면 상태를 기록한다.

  • package.json 또는 프로젝트 실행 문서를 확인한다.
  • 처음부터 실패하던 항목과 수정 후 실패한 항목을 구분한다.
  • 보이는 오류 메시지를 숨기지 않는다.
03

최소 변경 계획을 확인한다

수정 파일, 구현 순서, 검증 방법을 확인한 뒤 첫 단계만 시작한다.

  • 기존 구조를 유지하는 방식을 우선한다.
  • 새 라이브러리와 대규모 리팩터링은 명확한 이유가 있을 때만 허용한다.
  • 이해하지 못한 설계가 나오면 쉬운 말로 다시 설명하게 한다.
04

한 단계씩 구현한다

한 번에 전체를 맡기지 않고 핵심 기능부터 작은 단위로 구현한다.

  • 변경 파일과 이유를 매번 확인한다.
  • 단계가 끝날 때마다 관련 테스트를 실행한다.
  • 오류가 발생하면 정확한 오류 메시지를 기준으로 수정한다.
05

화면과 예외 상황을 직접 본다

테스트 통과만으로 끝내지 않고 실제 브라우저에서 사용자 흐름을 확인한다.

  • 정상 입력, 빈 입력, 잘못된 입력, 결과 없음
  • 로딩, 오류, 반복 실행, 긴 텍스트
  • 콘솔 오류와 화면 깨짐 여부
06

최종 diff와 전체 검증을 한다

요구사항 누락, 과도한 구현, 불필요한 파일, 비밀값 노출과 인계 내용을 확인한다.

  • 전체 테스트와 빌드를 다시 실행한다.
  • AI가 추측해서 만든 API나 기능이 없는지 확인한다.
  • 중요한 결정, 남은 한계, 롤백 방법을 팀에 남긴다.

작업 주기 배분

작업 크기와 관계없이 구현에만 몰리지 않도록 전체 주기를 비율로 나눈다.

모두 구현하라는 뜻이 아니라, 확인 여부와 이유를 알고 있어야 한다.

직접 확인

기능

상태

리뷰·인계 전 설명

코드만 넘기지 않고 판단과 검증 결과를 동료가 이어받을 수 있게 설명한다.

팀 공유

무엇을 바꿨나요?

변경한 기능, 파일, 사용자 흐름을 짧게 설명한다.

왜 이 방식인가요?

기존 구조 유지, 구현 범위, 다른 선택지를 쓰지 않은 이유를 말한다.

예외는 어떻게 처리했나요?

빈 입력, 실패, 로딩, 결과 없음 중 실제로 확인한 내용을 답한다.

어떻게 검증했나요?

실행한 테스트 명령과 브라우저에서 확인한 흐름을 구체적으로 말한다.

AI 제안을 그대로 썼나요?

검토 후 수정하거나 제외한 부분과 그 이유를 설명한다.

남은 한계는 무엇인가요?

못 한 부분을 숨기지 말고 시간과 범위를 기준으로 솔직하게 답한다.

마지막에는 AI 창을 보지 않고 60초 동안 설명한다. 핵심 파일의 역할, 선택한 방식, 예외 처리, 직접 실행한 검증과 남은 한계를 실제 코드와 실행 결과를 근거로 자기 말로 설명한다. 막히는 부분이 있으면 제출이나 인계 전에 코드를 다시 확인한다.

AI의 작업 범위와 사람이 승인해야 할 경계를 먼저 정한다.

배포, 인증, 권한, 데이터 삭제와 외부 전송처럼 영향이 큰 변경은 별도 검토와 담당자 승인을 거친다.

결정 근거, 실행한 테스트, 남은 한계와 롤백 방법을 이슈·PR·작업 문서에 남긴다.
